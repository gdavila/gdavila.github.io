Paris-traceroute

Paris-traceroute is a network tool that discovers the path packets follow across an IP network. Unlike classic traceroute, paris-traceroute guarantees that all probes follow the same path, thereby avoiding the artifacts introduced by load balancers. Details about these problems and the advantages of the tool are available on the official website.

Today, the paris-traceroute methodology is also implemented in other Internet measurement tools, such as Scamper and tracebox, and in several Internet measurement platforms, such as M-Lab and Archipelago.

In this post, we do not study paris-traceroute itself. Instead, we describe in detail how the fields of the IP datagram behave in the probes that paris-traceroute sends (forward path) and in the replies it receives (return path).

Per-flow load balancing

When IP packets traverse the Internet, they may follow different paths even when their source IP (IP::src) and destination IP (IP::dst) are the same. Typically, this is due to:

  1. Per-packet load balancing
  2. Per-flow load balancing

Per-packet load balancing distributes IP datagrams according to their order of arrival at the router. We do not cover this type of load balancing here.

Per-flow load balancing, on the other hand, relies on a hash (or flow-id) computed from certain fields of the IP datagram. Table 1 summarizes these fields for the IP, TCP, UDP and ICMP protocols. In short, if these fields remain constant across packets, all packets follow the same flow. The table also shows the fields that paris-traceroute uses as an identifier. This identifier is unique for each packet and allows us to tell apart several paris-traceroute probes originated from the same host. We mention it only to keep in mind that the identifier is a field that cannot remain constant. For instance:

  • For UDP, packets are identified by the checksum (UDP::checksum).
  • For ICMP, by the Identifier and Sequence Number (ICMP::identifier, ICMP::seqNumber).
  • For TCP, by the Sequence Number (TCP::seqNumber).

Header Fields Per-flow load balancing Varied by Paris-traceroute
IP IP::TOS, IP::protocol, IP::src, IP::dst NA
UDP UDP::srcPort, UDP::DstPort UDP::checksum
ICMP ICMP::Code, ICMP::checksum ICMP::identifier, ICMP::seqNumber
TCP TCP::srcPort, TCP::dstPort TCP::seqNumber

Taking as an example a UDP-based paris-traceroute between the same source and destination, the forward probes keep:

  • constant the fields IP::TOS, IP::protocol, IP::src, IP::dst, UDP::srcPort, UDP::DstPort;
  • variable the field UDP::checksum, which is used to tell one packet from another.

In the next section, we use UDP-based paris-traceroute as an example to explain in detail how probes are built to control the UDP::checksum, and how the return messages (ICMP time exceeded) behave with respect to per-flow load balancers.

Paris-traceroute UDP

Forward message: IPsrc -> IPdst (UDP)

The UDP probe of paris-traceroute alters the checksum to use it as an identifier of each probe sent. In turn, the checksum depends on several fields of the IP and UDP headers:


UDP::checksum = f (
                   IP::src, IP::dst, IP::reserved, IP::protocol, 
                   UDP::src, UDP::dst, UDP::length, UDP::data  
                        )

Here, f() is the function that computes the checksum. Recall that the checksum is computed by summing the involved fields in 16-bit words and taking the one's complement of the final result.

Among the fields involved in the checksum (UDP::checksum), the only one that is not constant is the payload (UDP::data), since the other fields stay constant to preserve the same flow-id.

In other words, UDP::data is the only field available to manipulate the resulting checksum. In practice, paris-traceroute adds a tag to UDP::data, which is then reflected in UDP::checksum and serves as the paris-traceroute identifier. This tag is copied into the first two bytes of UDP::data and matches the value assigned to IP::Identification.

Note: We verified this behavior with paris-traceroute ver. 0.9-dev.

Return message: IPhop -> IPsrc (icmpTimeExceeded)

The UDP paris-traceroute probes sent from the source reveal the IP hops along the path to the destination. In the previous section, we explained how the forward probes keep UDP::src, UDP::dst and UDP::length constant, while varying UDP::data and UDP::checksum. This ensures that all forward packets belong to the same flow (i.e., the same flow-id). However, this condition is not enough to ensure that the ICMP time exceeded replies also follow a single flow. Below, we walk through what happens with the return datagrams.

According to the authors of paris-traceroute, and as Table 1 shows, several ICMP time exceeded messages (originated at the same hop) belong to the same flow only if they keep the following fields constant:

  • ICMP::code
  • ICMP::checksum

   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+
   |                             unused                            |

   |      IP::header(*)+ 64/128 bits of Original Data Datagram(*)  |
   +-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+-+

   (*) Vary from message to message in paris-traceroute

In practice, the ICMP::code field of the reply remains constant (see ICMP Time Exceeded Message). For the ICMP::checksum of the return message to also remain constant, however, some additional conditions must hold.

For instance, we know that ICMP::checksum depends on:

ICMP::checksum = f (ICMP::type , ICMP::code , ICMP::payload)

We also know that the ICMP time exceeded message carries as payload the IP header of the original datagram plus the first 64 bits of the UDP header:

 ICMP::payload = IP::header + UDP::header

Given this, ICMP::checksum can remain constant thanks to one property of the checksum computation: if we add an already computed checksum to the values used to compute it, the result is always 0xFFFF. This property partially holds for the fields that make up the ICMP::payload of the return message, i.e.:

  • The sum of all fields of the IP header (see IP Header) of the original datagram (including IP::checksum) is always 0xFFFF.

  • The sum of the first 48 bits of the UDP header is also constant (see UDP Header), since most UDP::header fields (UDP::src, UDP::dst, UDP::length) do not change, to keep the forward flow-id constant. Hence, if we sum all fields of UDP::header, we obtain:

UDP::src + UDP::dst + UDP::len + UDP::checksum + UDP::data = \(k_1\) + UDP::checksum + UDP::data

                 |     Length      |  Checksum (*)   |

                 |                Data  (*)          |
                 |                                   |
                 +--------+--------+--------+--------+   
                 
  (*) Fields that vary from message to message in paris-traceroute
  • The constant \(k_1\) is the sum of the values that paris-traceroute keeps constant for a given source and destination.
  • The UDP::checksum field, on the other hand, varies from message to message because it is used as the identifier. However, since it depends only on the value of the UDP::data field, the sum of these two values also reduces to a constant \(k_2\) = UDP::checksum + UDP::data. In this case, \(k_2\) does not reduce to 0xFFFF as with the IP header, because the available terms are not all the fields used to compute UDP::checksum. Nevertheless, the missing fields (IP::src, IP::dst, IP::protocol, UDP::length) are always constant. Thereby, if ICMP::payload includes the only varying value (UDP::data), the sum of these two values always reduces to the same constant \(k_2\), which gives:

(UDP::src + UDP::dst + UDP::len) + (UDP::checksum + UDP::data) = \(k_1\) + \(k_2\) = \(k\)

As a result, ICMP::checksum is always computed over the same sum \(k\), which keeps it constant, and therefore all ICMP time exceeded packets belong to the same flow-id. Note that, for this to hold, the ICMP message must include UDP::data in its payload, since without it UDP::checksum lacks the term needed for both values to reduce to the constant \(k_2\).

The exception, where ICMP time exceeded messages from the same hop do not belong to the same flow-id (i.e., they carry different ICMP::checksum values), occurs when UDP::data is not included in the ICMP reply. This happens when network devices only quote the first 64 bits of the IP::payload of the original datagram (RFC792) and do not support RFC4884. In other words, supporting RFC4884 is a necessary condition to ensure that all return messages follow the same flow.

TCP Paris-traceroute

The mechanism is fully analogous to the UDP case. With TCP, TCP::seqNumber is used as the identifier, and it is manipulated through TCP::data. For the return messages to follow the same flow, RFC4884 must also be supported.

ICMP Paris-traceroute

This case differs from the previous ones in its implementation, but produces the same results. With ICMP, ICMP::identifier and ICMP::seqNumber are used as the identifier, and the ICMP::data field is used to always produce the same ICMP::checksum value, thereby ensuring the same flow-id for the forward probes.

In the return packet, the ICMP::data field is needed for the sum involved in the checksum of the return packet to remain constant. Hence, for the return messages to follow the same flow, RFC4884 must also be supported.
